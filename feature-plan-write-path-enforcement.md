# Blueprint: Server-Side Write-Path Enforcement — Period Lock, Late-Entry Validation & Completeness Recording

> **This ticket contains THREE phases. Complete Phase A fully before Phase B, and Phase B before Phase C.**
> **Tier 1 — BLOCKING.** This is the highest-priority DCAA fix. Do not start any Tier 2 (control plane / billing) blueprint until this is merged and verified.

## 1. Architectural Overview & DCAA Impact

### The Problem

The timesheet write path has two server-side enforcement holes. The UI prevents both, but the server actions are exposed HTTP endpoints (`'use server'`) and can be called directly with a crafted payload.

**Gap A — Certified periods are still writable.**
`saveTimesheetBatch()` and `saveTimesheetEntry()` in `src/server/actions/timesheet.ts` validate future dates, CLIN assignment, and optimistic concurrency — but **never check the period's status**. A period that has been `submitted` (employee-certified) or `approved` (supervisor-certified) can still receive new revisions via a direct call. The UI gates this in `HourCell.tsx` (`isEditable = status === 'draft' || 'rejected'`), but the server does not. An auditor who discovers that certified timesheets remain mutable will reject the entire audit trail.

**Gap B — The mandatory late-entry reason code can be bypassed.**
The late-entry determination is made on the client and passed to the server as `isLateEntry: boolean` (`saveTimesheetBatch` param at `src/server/actions/timesheet.ts:217`, applied at `:313`). The server trusts this flag. A client that sets `isLateEntry: false` on a back-dated first entry will write the entry **without** the DCAA-required `changeReasonCode` and `comment`. The server must recompute late-entry status from authoritative data (the entry date and the existing revision history), not trust the client.

**Gap C — Completeness / total-time-accounting warnings are not recorded.**
Completeness checks (missing workdays, abnormally low hours, FLSA-exempt uncompensated OT) are computed only in the UI (`TimesheetToolbar.tsx`, `SubmitModal.tsx`) and appended to the free-text submission comment. They are **advisory and non-blocking by design** (per the architect's decision), but today they are not durably attached to the period record for the audit trail. This phase persists a structured completeness snapshot at submission time without blocking submission.

### DCAA Compliance Requirements

| Requirement | Reference | Gap |
|---|---|---|
| Once certified, a timesheet cannot be silently altered | CAS 418 / audit-trail integrity; CONTEXT.md "Append-Only Architecture" | Gap A |
| Corrections and late entries require a reason code + author | DCAA MAAR 6 (labor); CONTEXT.md "Daily Time Entry" | Gap B |
| Total Time Accounting incl. uncompensated OT for FLSA-exempt | FLSA / DCAA total-time-accounting | Gap C |

### Design Decisions

1. **Reuse the existing status reader.** `getPeriodStatus(userId, periodStart)` already exists in `src/server/actions/periods.ts:33` and returns a `PeriodInfo` with a `status` field. The new guard wraps it — do **not** write a new query.

2. **Fail-secure on the write path.** If the period is `submitted` or `approved`, the save throws before any insert. The client surfaces the error via the existing notification system.

3. **Server is the source of truth for "late".** The server recomputes late-entry status as: *the entry date is before today AND this is the first-ever revision for that (user, charge code, date) cell.* The client's `isLateEntry` flag is ignored. The existing per-cell `MAX(revisionNumber)` query already runs in `saveTimesheetBatch` (at `:290`) — reuse its result rather than adding a query.

4. **Reason codes become mandatory server-side.** When the server determines an entry is an **edit** (existing revision > 0) or a **late entry**, `changeReasonCode` must be present and non-empty, else throw. This closes Gap B definitively.

5. **Completeness is recorded, not enforced.** Per the architect's decision, submission is **not** blocked by completeness warnings. Instead, a structured warnings snapshot is written to a new nullable column on `timesheet_periods`. This requires a migration (additive, nullable — safe).

6. **No change to the append-only model.** Every save still inserts a new row with an incremented `revisionNumber`. Nothing in this blueprint updates or deletes timesheet entries.

## Phase B: Server-Side Late-Entry Recomputation & Mandatory Reason Code

### Problem
The server trusts the client's `isLateEntry` flag and only conditionally requires a reason code, so a crafted request can write a back-dated entry with no reason code.

### Execution Steps

    // Get current max revision

      .select({ maxRevision: sql<number>`COALESCE(MAX(${timesheetEntries.revisionNumber}), 0)` })

Replace the whole loop body with the version below. The changes: (1) compute `priorRevision` from the DB, (2) compute `serverIsEdit` and `serverIsLate` server-side, (3) require a reason code when either is true, (4) stop reading `cell.isEdit` / `cell.isLateEntry` for the authoritative decision.

```typescript
  for (const cell of data.cells) {
    const entryDate = start.add(cell.dayIndex, 'day').toDate();
    const entryId = cell.clinId ?? cell.indirectCodeId ?? '';

    // Get current max revision
    const existing = await db
      .select({ maxRevision: sql<number>`COALESCE(MAX(${timesheetEntries.revisionNumber}), 0)` })
      .from(timesheetEntries)
      .where(
        and(
          eq(timesheetEntries.userId, data.userId),
          cell.clinId
            ? eq(timesheetEntries.clinId, cell.clinId)
            : eq(timesheetEntries.indirectCodeId, cell.indirectCodeId!),
          eq(timesheetEntries.entryDate, entryDate),
        )
      );

    const priorRevision = existing[0]?.maxRevision ?? 0;
    const nextRevision = priorRevision + 1;

    // Server-authoritative reason-code determination (ignore client flags).
    // An entry is an EDIT if a prior revision exists.
    // An entry is a LATE entry if it is the first revision for a past-dated cell.
    const serverIsEdit = priorRevision > 0;
    const serverIsLate =
      priorRevision === 0 && dayjs(entryDate).isBefore(today, 'day');
    const requiresReason = serverIsEdit || serverIsLate;

    if (requiresReason) {
      const code = (data.changeReasonCode ?? '').trim();
      if (!code) {
        const label = dayjs(entryDate).format('MMM D, YYYY');
        throw new Error(
          serverIsLate
            ? `A reason code is required for the late entry on ${label}.`
            : `A reason code is required to edit the entry on ${label}.`
        );
      }
    }

    await db.insert(timesheetEntries).values({
      userId: data.userId,
      clinId: cell.clinId ?? null,
      slinId: cell.slinId ?? null,
      indirectCodeId: cell.indirectCodeId ?? null,
      entryDate,
      hours: cell.hours.toString(),
      revisionNumber: nextRevision,
      changeReasonCode: requiresReason ? (data.changeReasonCode ?? undefined) : undefined,
      comment: requiresReason ? (data.comment ?? undefined) : undefined,
      createdBy: data.userId,
    });

    const key = `${entryId}-${cell.dayIndex}`;
    newRevisions[key] = nextRevision;
  }
```
